# kitty-companion-r6-schedule-edit — editing a schedule stops deleting the fields the editor never sent

**Initiative:** kitty-companion-r6-v1
**Owner:** builder
**Depends on:** kitty-companion-r6-experts
**Free or paid:** free

## What Jacob can do after this

Rename a schedule or change its time from Automations without silently wiping
the timezone on the morning brief or the description on a loop.

## Why this is the next thing

The Automations surface edits schedules through `PATCH /cron/schedule/{sid}`.
The request model's `timezone` defaults to `None` (`gateway/routes/cron.py:16`),
the route resolves that to `{}` (`:19-29`, `:95-107`), and the update path then
replaces the stored metadata wholesale:

- `gateway/undo_journal.py:414-416` — `metadata or {}`
- `gateway/cron.py:276-296` — `SET ... metadata = ?`

The frontend editor never sends a timezone
(`gateway/kitty-chat/src/lib/gateway.ts:1365-1377`), so every edit from the
product wipes the schedule's metadata. Two concrete losses:

- the seeded morning brief carries `{"timezone": ...}` (`gateway/app.py:341-350`);
  one edit drops it back to the profile default;
- a loop created from `POST /loops` carries `description` and
  `interval_minutes` (`gateway/routes/loops.py:57-67`); one edit empties the
  description the Loops panel displays.

Reproduced on current `main` (2026-09-17, `7dd703c7`) through the real route
function, in a temporary case file that was deleted after capture; this packet
writes it to `tests/test_cron_schedule_edit.py`:

```
$ python -m pytest -q tests/test_cron_schedule_edit.py::test_repro_edit_without_timezone_keeps_stored_metadata
E       AssertionError: assert None == 'America/Regina'
E        +  where None = {}.get('timezone')
tests/test_cron_schedule_edit.py:...
```

The existing test `tests/test_cron_run_routes.py:113-132` only pins the case
where the request *supplies* a timezone and it is replaced — that behaviour is
correct and stays. No test covers the omitting case.

## Plan

1. Write the failing tests first in `tests/test_cron_schedule_edit.py`: an edit
   with no timezone on a schedule holding `{"timezone": "America/Regina"}`, an
   edit with no timezone on a schedule holding a loop `description`, and the
   existing replacement case restated at the route level. Confirm the first two
   fail with the quoted assertion before touching product code.
2. Resolve metadata inside `gateway/routes/cron.py` before dispatching: read the
   schedule's current row from `cron.list_schedules()`, and when the request
   does not name a timezone pass the stored metadata through unchanged; when the
   request does name one, pass the stored metadata with `timezone` replaced.
   Do not change `cron.update`'s replacement semantics — the undo restore path
   (`gateway/undo_journal.py:226-234`) depends on an explicit dict meaning
   "make it exactly this".
3. Keep the create path (`POST /cron/schedule`) as it is: a new schedule with no
   timezone still stores no timezone metadata. The existing create test
   (`tests/test_cron_run_routes.py:63-73`) is the fence for that.
4. Keep the missing-schedule behaviour: `UndoNotFound` still becomes the
   existing 404 with its current message, so the UI's error text does not
   change.
5. Run the new file and `tests/test_cron_run_routes.py` together.

## Not in scope

Adding a timezone picker or any other control to `CronPanel.tsx` — this packet
changes no frontend source, and the UI merely stops destroying data it never
sent. Clearing a timezone on purpose; the request shape cannot express
"remove the timezone" and inventing a sentinel for it is a different contract
decision. The dead `fetchActionWhy` helper, orphaned `/cron/runs` history
routes, and monitor pause control are separate findings, not this packet. This
packet edits existing files only and creates no new production files.

## Verification

**Tier 1 — mechanical.**

```

```

Today the command exits 4: `tests/test_cron_schedule_edit.py` does not exist yet
and is inside this packet's fence. The quoted repro is that file's failing state
on unfixed product code. After the change both files pass, and
`tests/test_cron_run_routes.py` passes **unchanged**, including the
replacement-when-supplied test.

**Tier 2 — running app.** Existing Automations smoke coverage must still pass in
CI, proving edit/save from the surface still works end to end; this packet adds
no UI. If the surface is driven by hand during acceptance, the check is: edit
the morning brief's time, reopen the row, and confirm the stored timezone is
still there in `/cron/schedules`.

**Tier 3 — product acceptance.** Not triggered: no native UI source changes, so
`scripts/pr_policy.py`'s product-acceptance gate does not apply. The mechanical
gate is the proof. Nothing here renders a control or a layout, so the
control-completeness and overflow criteria do not apply; the user-visible effect
is that an edit no longer destroys stored fields.

## Stop condition

Stop and escalate if preserving the stored metadata cannot be done from the
route with the existing `cron.list_schedules()` read — if it needs a second
schedule store, a new query path, or a request-model sentinel that the current
client cannot send, the contract question is bigger than this packet and belongs
to Jacob.

## Recovery

Revert `gateway/routes/cron.py` to `HEAD` and re-run. The new test file is the
durable part: it encodes "an edit keeps what it did not send" and is worth
keeping red rather than deleting if the fix is reverted. Existing schedules
already holding `{}` metadata cannot be repaired by this packet and are not its
responsibility; only the edit path is.
