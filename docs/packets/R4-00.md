## What Jacob can do after this

Open Kitty and see the studio shell — warm cream by day, an authored deep night
mode, dark grounded navigation, one cat — instead of the current chrome.

## Why this is the next thing

The design is decided and written down. `docs/frontend/KITTY_STUDIO_EXPERIENCE.md`
is marked **accepted** as of 2026-09-11 and is the canonical brief until Jacob
changes it. What has never happened is applying it to the running product.

The work is also already half-done and parked. Branch
`design/kitty-reimagine-20260910` carries real shell code — `BottomNav.tsx`,
`Rail.tsx`, `Skeleton.tsx`, `Toast.tsx` and their tests — across commits
`d2f5cb72`, `16afc556` and `2997fe79`. It is 5 commits behind current main and
was deliberately held: the plan on that same branch says the shell commits are
"salvage input, not merge authority" and must not land ahead of R-3. R-3 closed
when PR #870 merged, so the hold is over.

Salvage, do not replay. That branch predates everything R-3 changed, so its Home
and Chat assumptions are stale even where its shell behaviour is still right.

## Plan

1. Start from current `main`, not from the design branch. Read
   `d2f5cb72`, `16afc556` and `2997fe79` and port only the shell behaviour that
   is still correct against today's components.
2. Write the failing theme test first. Assert token *roles* rather than exact
   hex values — the brief says the values may be tuned during browser acceptance,
   so pinning a hex string would make legitimate tuning look like a regression.
   Assert instead that canvas and surface are defined, differ, and are not pure
   white, and that the night block defines every token name the day block does.
3. Apply the tokens in `gateway/kitty-chat/src/app/globals.css`, keeping the
   success, warning and destructive semantic colours independent of the brand
   accent.
4. Bring `Rail.tsx`, `BottomNav.tsx` and `TopBar.tsx` to the grounded navigation
   shape without changing a single navigation destination or id. The test that
   pins the existing destination set is what makes this safe.
5. Leave exactly one persistent Kitty anchor via the existing `CrayonCat` seam.
   Do not build the contextual mini-chat; the brief defers it and it would become
   a second chat runtime.

## Not in scope

Home composition (R4-01) and Chat layout (R4-02). Merging

## Verification

**Tier 1 — mechanical.**

```
cd gateway/kitty-chat && npx vitest run tests/Rail.test.tsx tests/BottomNav.test.tsx tests/CrayonCat.test.tsx tests/StudioTheme.test.ts --reporter=dot
cd gateway/kitty-chat && npx tsc --noEmit
```

`tests/StudioTheme.test.ts` does not exist yet; it is inside this packet's fence
and the packet creates it. Today the first command fails on that missing file,
which is the packet's honest red state.

One environment note that will otherwise cost an attempt: if the shell exports
`NODE_ENV=production`, React resolves its production build, `act` is missing and
every rendering test fails with `React.act is not a function` — roughly 650
failures that have nothing to do with this work. A fix pinning `NODE_ENV` in the
vitest config is already written in `.worktrees/fix-ui-test-env-20260916`. If
that failure appears, it is that, not this packet.

**Tier 2 — running app.** Existing smoke specs under
`gateway/kitty-chat/tests/smoke/` must still pass unchanged, proving the shell
kept every destination it had. CI runs them as `browser-smoke` across the
`desktop` and `mobile` projects.

**Tier 3 — product acceptance.** User-facing, so `scripts/pr_policy.py` requires
a product acceptance record from a reviewer who did not implement the change. An
interactive agent session that did not run this packet can drive that check in
the running app and record the evidence. Publication and merge remain Jacob's
call; this packet does not push, open a PR or merge.

## Stop condition

Stop and escalate if applying the token contract cannot be done without changing
a navigation destination or an element id that another surface depends on. The
brief is a presentation change; the moment it starts moving destinations it has
become a routing change, and that is a different packet with a different blast
radius.

## Recovery

Every change is presentation-layer and confined to this packet's fence. Revert
the changed files to `HEAD` and re-run. The salvage source branch is read-only
here and cannot be damaged by a failed attempt. If the theme lands but the shell
does not, that is a coherent stopping point: the tokens are inert until a
component uses them.
