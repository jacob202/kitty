**Initiative:** kitty-companion-r6-v2 (supersedes kitty-companion-r6-v1, applied
2026-09-17 and paused; review added the incomplete-reply criterion below)
**Owner:** builder
**Depends on:** none inside this manifest
**Free or paid:** free

## What Jacob can do after this

Leave the expert watchers running: when a model answer does not match the agreed
reply format, the evaluation ends with a recorded reason instead of crashing,
losing a watched CSV to the dead-letter queue, or re-asking the same capture on
every poll.

## Why this is the next thing

This is a live crash, not a theoretical one. `_evaluate_and_emit` binds
`headline`, `action` and `analysis` only inside `if "[Headline]" in response:`
(`gateway/expert_proactive.py:391-413`) and then uses all three unconditionally
when it emits (`:419-427`). Any reply that is neither `NO`/`ABORT` nor a
formatted headline — plain prose, or a `SEARCH:` reply with learning disabled —
walks off the end of that guard and raises `UnboundLocalError` at `:423`.

Reproduced hermetically on current `main` (2026-09-17, `7dd703c7`), with the LLM
stubbed to return one sentence of prose and signal emission recorded. The cases
were captured in a temporary file that was deleted after capture; this packet
writes them to `tests/test_expert_proactive_replies.py`:

```
$ python -m pytest -q tests/test_expert_proactive_replies.py::test_repro_unformatted_reply_does_not_raise
E       UnboundLocalError: cannot access local variable 'headline' where it is not associated with a value
gateway/expert_proactive.py:423: UnboundLocalError
```

What that exception then does depends on which path raised it, and both outcomes
are bad in ways Jacob cannot see:

- **Inbox path** (`:115-128`): the exception is caught, the entry is reset to
  `"new"`, and the next poll claims it again and calls the model again. A model
  that keeps answering in prose keeps burning calls on the same capture.
- **Watch-directory path** (`:158-181`): the exception is caught by the
  *file-reading* handler, which moves Jacob's CSV to the dead-letter queue and
  emits `expert.error` (`:176-181`). The file is not read because the model was
  badly formatted; it disappears because of it. Reproduced:

```
$ python -m pytest -q tests/test_expert_proactive_replies.py::test_repro_watch_file_survives_unformatted_reply
E       AssertionError: watch file was moved to the dead-letter queue
E       assert False
```

The only existing test (`tests/test_expert_proactive.py::test_proactive_polling`)
drives the happy path where every reply is either `NO` or correctly formatted, so
neither failure is covered. The crash is in the companion's proactive-surfacing
path — the exact thing R-6 exists to make trustworthy — and the file loss is
data loss on Jacob's iCloud CSV watch folder.

## Plan

1. Write the failing tests first, in a new file
   `tests/test_expert_proactive_replies.py`, mirroring the fixture style of
   `tests/test_expert_proactive.py`: prose reply, `SEARCH:` reply with
   `learning_enabled=False`, watch-directory prose reply, inbox prose reply.
   Confirm they fail with the quoted `UnboundLocalError` before touching product
   code.
2. In `gateway/expert_proactive.py`, split the reply handling into an explicit
   outcome: `NO`/`ABORT` → no signal; a formatted `[Headline]` reply → parse and
   emit exactly as today; anything else → log one warning naming the expert and
   the dedupe key, emit nothing, mark the reply consumed (inbox entry triaged /
   file cursor advanced for this reply, reusing the existing success-path
   bookkeeping — no second bookkeeping path), and return normally. Do not raise. A reply that
   parses to an empty headline, or to no action and no analysis, is *anything
   else* — an incomplete answer must not reach the signal store with missing
   fields just because the `[Headline]` marker is present.
3. Do not log or persist the model's reply text. The repository has already paid
   for this mistake once (`truncation-is-not-redaction`); a warning that says
   "reply did not match the agreed format" is the whole record.
4. Do not set the topic cooldown on a skipped reply — no signal was emitted, and
   the inbox entry is marked triaged or the file cursor advances, so nothing
   repeats anyway.
5. Keep `_poll_single_expert`'s existing success path as the only bookkeeping
   for inbox triage and watch-cursor advance; the unparseable reply above
   flows through that same path (no exception, so no reset to `"new"` and no
   dead-letter move), not a second bookkeeping path.
6. Run the gate: the new file and the existing regression file must pass
   together.

## Not in scope

Scheduling `experts.poll` on a timer. It is registered (`gateway/app.py:316`)
and deliberately never seeded into the startup schedule list
(`gateway/app.py:341-356`); `_evaluate_and_emit` can reach a hosted model, so
making it recur on its own is a spend decision for Jacob, not a Builder packet.
Also out of scope: `_already_evaluated`'s permanent `False` stub, the expert
snooze/pause routes, the expert signal UI, and any change to
`gateway/expert_state.py`. An adversarial review on 2026-09-17 separately found
that `_is_duplicate_signal` (`gateway/expert_proactive.py:261`) calls the
synchronous `llm_client.call_llm` from the async poll path with no
`asyncio.to_thread`, stalling the event loop; that is a distinct defect in the
same module and is not this packet's subject. This packet edits existing files
only and creates no new production files.

**Tier 3 — product acceptance.** Not triggered: no native UI source changes, so

matters here is the mechanical gate plus the reproduced dead-letter assertion.

and overflow criteria do not apply; the user-visible effect is confined to which
signals the store holds and to the dead-letter queue the file never reaches.

## Stop condition

Stop and escalate if ending an unparseable evaluation cleanly requires a place to
record the reason that does not exist — a new signal kind, a new store, or a
schema change. The existing lifecycle already has the two states this needs
(no-signal and evaluated); if it genuinely does not, that is a separate finding
with its own packet.

## Recovery

Both files are ordinary Python. Revert `gateway/expert_proactive.py` to `HEAD`
and re-run; the new test file is red and expressive and is worth keeping even
then, because it is the only coverage of the reply-classification contract. If
only part of the fix lands, prefer a coherent "skip on unparseable reply" over a
half-guarded path that still references unbound names.
