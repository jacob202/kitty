# kitty-studio-r5-proto — put the picture where the work is

**Initiative:** kitty-studio-r5-v1
**Owner:** builder, once builder-frontend-proof-v1 has landed. Interactive before that.
**Depends on:** none inside this manifest. Across manifests: BFP-04-authoring for the gates, and kitty-studio-r4-v1 for the shell and tokens these surfaces inherit.
**Free or paid:** free

## What Jacob can do after this

Open Image Lab and see the thing he is making, instead of the settings for making
it.

## Why this is the next thing

Image Lab is the one surface the brief lets be visually dense, because there the
imagery *is* the work rather than decoration. The brief fixes the order: create
and reference context, then the current series, then the selected result, then
what to do next — with model, provider, cost and provenance reachable but
subordinate unless a decision depends on them.

Today that order is not enforced anywhere, and nothing stops configuration
leading the page. This packet is the prototype for the initiative: it settles the
arrangement against fixtures before the full recomposition builds on it, so a
wrong hierarchy is discovered cheaply.

The functional contracts are not in question here. `docs/packets/OK-IMAGE-01.md`
describes the create-to-result loop and is an unactivated draft; this packet does
not re-derive it, does not activate it, and adds no pipeline capability.

## Plan

1. Freeze the hierarchy in tests first, against two fixtures: a session with no
   result, and a session with a real succeeded result.
2. With no result, create and reference controls lead and no result region
   renders at all. An empty result frame is the fake-preview failure in a
   different costume.
3. With a real result, the result and the current series take the dominant
   region and configuration becomes subordinate or collapsible.
4. Keep queued and running state visible across both arrangements — losing an
   in-flight job between states is the kind of bug that makes people press the
   button twice.
5. Move presentation only. `ImageLab`'s existing state, hooks and API calls stay
   as they are; the existing Image Lab tests passing unchanged is the assertion
   that proves it.

## Not in scope

Result actions and their availability rules — that is R5-01. Library — R5-02. Any
new provider, route, pipeline or image capability. Changing what the backend
reports about a job; only where that report appears on screen.

## Verification

**Tier 1 — mechanical.**

```
cd gateway/kitty-chat && npx vitest run tests/ImageLab.test.tsx tests/ImageLabLayout.test.tsx --reporter=dot
cd gateway/kitty-chat && npx tsc --noEmit
```

Both test files exist and pass today, so this is a real before-and-after: the new
hierarchy assertions fail until the arrangement changes, and the existing
assertions must keep passing throughout. A failure in the existing cases means
this packet rewired state it was supposed to leave alone.

**Tier 2 — running app.** The existing Image Lab smoke coverage must still pass,
proving the arrangement change did not break the create path in a browser.

**Tier 3 — product acceptance.** User-facing, so a reviewer who did not implement
it completes an image session in the running app and records the evidence. An
interactive agent session can do that. Merge stays Jacob's decision.

## Stop condition

Stop and escalate if the hierarchy cannot be expressed without moving state out
of `ImageLab` — if arranging the surface requires lifting or re-owning a hook.
That is a rewrite, not an arrangement, and it needs its own packet and its own
risk budget.

## Recovery

Presentation only: revert the changed components to `HEAD` and re-run. Keep the
two fixtures even if the arrangement reverts — they encode the with-result and
without-result contracts and are the durable part of this packet.
