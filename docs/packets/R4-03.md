# kitty-studio-r4-acceptance — prove the journey, not the screens

**Initiative:** kitty-studio-r4-v1
**Owner:** builder, once builder-frontend-proof-v1 has landed. Interactive before that.
**Depends on:** kitty-studio-r4-proto, kitty-studio-r4-home, kitty-studio-r4-chat
**Free or paid:** free

## What Jacob can do after this

Go Home, pick up a thread, talk to Kitty about it, come back, reload — and have
the product still know where he was, on the laptop and on the phone.

## Why this is the next thing

The three packets before this each prove their own surface. None of them proves
the seam between the surfaces, and the seam is where this kind of work usually
breaks: identities that survive a render but not a navigation, state that
survives a navigation but not a reload.

The brief says this outright — the redesign is not accepted from screenshots
alone, and the final judge is whether Jacob can open Kitty, understand where he
was, and jump into one of several live threads. That is a journey, so it needs a
journey test.

This packet adds coverage. It changes product code only where the coverage
exposes a real defect, and any such change is a finding worth recording rather
than a silent patch.

## Plan

1. Write the journey spec: Home, into a resumable context, into Chat, back to
   Home. Assert the same identities on both ends, then reload and assert again.
2. Cover both themes. The night theme is authored separately from day, so a
   journey that only runs in day proves half the product.
3. Assert the mechanical invariants the brief states as numbers rather than
   taste: no horizontal page overflow at iPhone-class widths, and persistent
   primary controls at least 44 pixels high. These are the criteria a reviewing
   agent can check without an opinion.
4. Cover one degraded source. The brief requires a degraded state to preserve
   context and offer the next useful action; a spec that only walks the happy
   path will not notice when it stops doing that.
5. Follow the repository's existing smoke conventions: route-stub the gateway
   calls the spec needs, answer `**/proxy/health` or the app never mounts, set
   `localStorage['kitty-onboarded'] = 'true'` before navigating, and scope
   `getByRole('alert')` to `main` because Next's route announcer is also an alert.

## Not in scope

Image Lab and Library, which are R-5 and have their own journey. Changing any
surface's composition to make a spec easier to write — if the spec is hard to
write because the product is wrong, that is a finding. Adding new fixtures beyond
those the journey needs.

## Verification

**Tier 1 — mechanical.**

```
cd gateway/kitty-chat && npx vitest run tests/HomeStudioComposition.test.tsx tests/ChatWorkspace.test.tsx --reporter=dot
cd gateway/kitty-chat && npx tsc --noEmit
```

These are the composition contracts from the two preceding packets; this packet
must not regress them. Playwright is deliberately not a Tier 1 gate: it needs a
served app and browser binaries, which is a poor fit for a ten-minute sandboxed
worker. Its home is Tier 2, in CI, where `browser-smoke` already runs every spec
under both viewport projects.

**Tier 2 — running app.** This packet's whole product is the Tier 2 artifact: the
journey spec under `gateway/kitty-chat/tests/smoke/`, green under `desktop` and
`mobile`, in both themes, including the degraded-source case.

**Tier 3 — product acceptance.** This is the packet where R-4 gets its acceptance
record. A reviewer who did not implement R-4 walks the journey in the running app
and records the evidence; an interactive agent session can do that, driving the
real UI rather than reading test output. Publication and merge remain Jacob's
decision.

## Stop condition

Stop and escalate if the journey cannot be walked because an identity genuinely
does not survive navigation or reload. That is a real product defect and it
belongs in its own packet with its own diagnosis — not hidden by relaxing the
spec until it passes. A journey test that was weakened to go green is worse than
no journey test, because it will be cited as evidence later.

## Recovery

The spec is additive: delete it and the product is exactly as it was. If it
exposes a defect mid-packet, record the defect, leave the spec failing, and stop.
A failing spec that names a real problem is a finished piece of work, and the
next session resumes from a red test with a written cause rather than from a
guess.
