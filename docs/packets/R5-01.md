# kitty-studio-r5-image — only offer what the backend can actually do

**Initiative:** kitty-studio-r5-v1
**Owner:** builder, once builder-frontend-proof-v1 has landed. Interactive before that.
**Depends on:** kitty-studio-r5-proto
**Free or paid:** free

## What Jacob can do after this

Pick a result and act on it — make variations, compare, upscale, use it as a
reference — and every button he can see actually works.

## Why this is the next thing

The prototype settles where things sit. This packet settles what they promise.

The brief's rule is narrow and strict: expose edit, inpaint, variations, compare,
upscale, use-as-reference, save and attach **only** when the real status, job and
result contracts say they are available. The repository's own standard says the
same thing more bluntly — a visible control either completes its task or is
disabled with a plain reason beside it, and a read-only card is a defect.

A control that looks available and does nothing is worse than a missing one,
because it teaches Jacob not to trust the surface. That is why this packet's
first criterion is an assertion about a control being *absent* when the contract
says unavailable, rather than an assertion about it being present when available.

## Plan

1. Write the unavailable-action fixture first and assert the control is absent or
   disabled-with-reason. Get that red before anything else.
2. Wire each result action to the availability the existing status, job and result
   contracts already report. Do not infer availability from the presence of a
   result; a succeeded result does not imply every operation is supported for it.
3. Handle the failed provider case: keep the session context on screen and offer a
   recovery path. The brief requires context and a next action; the standard
   forbids a raw status code being the message a person reads.
4. Keep provenance, route and cost reachable from a selected result without
   letting them lead the page — asserted over rendered order, not by eye.
5. Leave source and reference upload working exactly as it does; the existing
   upload test passing unchanged is the proof.

## Not in scope

Adding any new image operation, provider or route. Changing how availability is
computed on the backend — if a contract cannot report availability, that is a
finding and a separate packet, not something to guess at in the component.
Library, which is R5-02.

## Verification

**Tier 1 — mechanical.**

```
cd gateway/kitty-chat && npx vitest run tests/ImageLab.test.tsx tests/ImageLabLayout.test.tsx tests/ImageLabRecovery.test.tsx tests/ImageLabSourceUpload.test.tsx tests/ImageLabAnchorClear.test.tsx --reporter=dot
cd gateway/kitty-chat && npx tsc --noEmit
```

All five files exist and pass today. The recovery and upload suites are the
regression fence: this packet touches the surface they cover, so a failure there
afterwards is this packet's doing and not a flake.

**Tier 2 — running app.** A smoke run covering a new session, a restored session,
a running batch, a succeeded result and a failed provider — the five states where
an action's availability actually differs.

**Tier 3 — product acceptance.** User-facing; a reviewer who did not implement it
runs an image session in the running app, tries the offered actions, and records
the evidence. An interactive agent session can do that. Merge stays Jacob's.

## Stop condition

Stop and escalate if an action's availability cannot be determined from an
existing contract. Rendering it anyway and letting the click fail is the exact
defect this packet exists to remove, and inventing a client-side guess at
availability is the same defect with extra steps.

## Recovery

Revert the changed components to `HEAD`. Keep the unavailable-action fixture
regardless of what happens to the implementation; it is the assertion that stops
this class of defect coming back, and it is cheap to carry.
