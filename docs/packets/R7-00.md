## Why this is the next thing

`_cron_source` catches a schedule-read failure, logs a warning, and leaves
`schedule_count = 0` while returning the supervisor's status unchanged
(`gateway/health_surface.py:126-141`):

```python
status = supervisor.get_status("cron")
schedule_count = 0
try:
    schedule_count = len(cron.list_schedules())
except Exception as exc:
    logger.warning("health surface: cron schedule list failed: %s", exc)
return HealthDomain("cron", status["status"], reason=status["reason"],
                    detail={"schedules": schedule_count})
```

If the supervisor still believes the cron task is running — a read failure does
not stop the task — the domain reports `available` with `schedules: 0`. That is
exactly the class `REVIEW.md` names: a message that is true and unusable, and a
count that was not measured. The surface is served to the product by
`gateway/routes/status.py:54-57` and consumed by the UI health projection.

The supervisor's own status is not always `available`: it can already report
`stale`, `unavailable`, or `unknown`, and the surface orders those as more
severe than `degraded` (`_worst_status`, `gateway/health_surface.py:304-323`:
available < degraded < stale < unavailable < unknown). A failed schedule read
must not *improve* a domain whose scheduler is already reporting one of those
states; the read failure is additional evidence, not a replacement.

Reproduced on current `main` (2026-09-17, `7dd703c7`) by calling the domain with
a raising schedule read and an available supervisor, in a temporary case file
that was deleted after capture; this packet writes it to
`tests/test_health_surface_degraded.py`:

```
$ python -m pytest -q tests/test_health_surface_degraded.py::test_repro_cron_read_failure_is_reported
E       AssertionError: HealthDomain(name='cron', status='available', reason='task running', detail={'schedules': 0})
WARNING  kitty.health_surface:health_surface.py:135 health surface: cron schedule list failed: cron db locked
```

The healthy path is honest and tested — `tests/test_health_surface.py` covers
available, degraded and stale domains through injected sources. What is not
covered is the domain's own failure handling, which is where the lie lives.

## Plan

1. Write the failing tests first in `tests/test_health_surface_degraded.py`:
   (a) schedule read raises while the supervisor says available →
   (b) schedule read succeeds → status and measured count preserved;
   (c) schedule read raises while the supervisor reports `stale`, `unavailable`,
   and `unknown` → the supervisor's more severe status is retained, one case
   each. Confirm (a) fails with the quoted output before touching product code.
2. In `gateway/health_surface.py`, on a failed read return a domain whose status
   is the more severe of the supervisor's status and `degraded`, using the
   surface's existing severity order (`_worst_status`, `:304-323`) — `degraded`
   when the supervisor reports `available`, and the supervisor's own
   `stale`/`unavailable`/`unknown` when it is more severe. The reason is one
   plain sentence naming the read failure and its exception type — for example
   `"schedule list could not be read (RuntimeError)"`, plus the supervisor's
   plus the supervisor's
   status when that is the retained one — with `detail={"schedules": None}` (absent
   count, not a zero; the one UI consumer, `gateway.ts:2320`, reads the surface,
   not this domain's count directly, so no frontend change is needed); the
   exception message goes to the log, not to the reason string. Keep the scope
   to this domain; do not restructure the surface.
3. Leave the successful path byte-identical: same status, same reason, same
   measured count.
4. A read failure must not raise out of the surface and must not 500 the
   endpoint; the domain is the honest carrier.
5. Run the new file and the existing `tests/test_health_surface.py` together.
