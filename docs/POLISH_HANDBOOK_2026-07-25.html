PrefaceHow to read this

Polish is not a layer applied at the end. In every project studied, it is a scar — the residue of a specific failure that a specific user reported, argued about, and got fixed. This document collects the scars.

Each theme runs the same six beats: what the best projects do, why they landed there, the evidence, the reusable pattern, where Kitty stands, and at most two proposals. The evidence dump behind it is ~/kb/raw/2026-07-25-polish-evidence.md.

The corpus

open-webui · LibreChat · khoj · continue · cline · aider · NextChat · zed. Chosen for age and traffic, not feature parity with Kitty. Two of them (aider, cline) are agents rather than chat apps, which is where the agent-visibility evidence comes from.

The one thing to take away

Across eight independent codebases, the defects that make software feel unfinished are overwhelmingly signal defects, not capability defects. The model answered. The request succeeded. The command ran. But nothing on screen said so, or something on screen said the wrong thing, and the user concluded the product was broken. Six of the eight themes below are variations on this.

Theme 01Streaming and latency masking

The hardest-won knowledge in this corpus. Every project independently discovered that naive streaming is quadratic, that batching the fix can make it feel worse, and that the scroll position is part of the streaming problem, not a separate one.

What the best projects do

They treat a streaming response as a delta feed applied to a stable document, not as a document re-rendered per token. Concretely: send deltas rather than the cumulative buffer, coalesce DOM writes to at most one per frame, memoize every message that isn't the streaming one, and give the stream an identity that survives the connection carrying it.

Why they converged there

Because someone measured it. Open WebUI's #23733 is the most complete accounting of the naive approach in the corpus:

"During an LLM streaming response, the backend re-serializes the entire accumulated output...on every SSE event."

"Total bytes on the wire for an N-token response scale as O(N²)."

"At 30 tok/s, the frontend main thread spends 600+ ms/sec re-parsing Markdown for content the user has already seen." open-webui#23733, 2026-04-14

Every number in this section is reported by those threads, not measured here. The report's headline figure — 120 GB of infrastructure traffic to deliver 10 MB of tokens, a 10,000× amplification — is that reporter's accounting of what the naive loop costs at scale. Profiling claimed in discussion #20878 puts the frontend cost at 504 markdown-parser runs and 401 KaTeX matches over a 20-second response, where one pass per frame would be about 60 per second. Neither figure was independently reproduced, and neither transfers to Kitty without a profile of Kitty.

The reversal that matters most

Open WebUI shipped the obvious fix and pulled it in one day.

DatePRWhat
2026-03-24#22947 "perf: batch history reactive updates to rAF in chatEventHandler" — replaced a direct store write with a requestAnimationFrame coalescer
2026-03-25#23016 Reverted it. Sole commit headline: "perf: fix double-RAF streaming display lag"

The coalescer was correct. It sat on top of an rAF that already existed further down the render path, and the resulting two-frame delay made streaming feel slower while measurably doing less work. Perceived latency beat measured throughput, and the maintainers chose accordingly, fast.

Scroll is a streaming problem

The single most-repeated complaint in the entire corpus. Four projects, six issues, same defect:

IssueTitle
open-webui#23990 (27c)Scrolling up jumps around in a conversation
open-webui#25761Implement scroll anchoring / stable reading view during fast generation
open-webui#1195Auto scroll fails to stop with small scroll amounts
khoj#1252Allow disabling auto-scroll on new token
cline#10450Chat auto-scrolls to top when processing larger responses
NextChat#3409Wrong loading while scrolling
"If a user tries to focus and read an answer from the top while it is actively streaming, the layout constantly jumps, causing severe eye strain."

"the only workaround is a manual user gesture: flicking the mouse wheel upward the millisecond text generation begins to force-trigger the internal scroll lock." open-webui#25761

khoj#1252 names the anti-pattern in a single line — "chatContainer.scrollTop = chatContainer.scrollHeight; This ensures the latest message is always visible — but it ignores whether the user has manually scrolled up." The fix everywhere is the same shape: a near-bottom test that gates the scroll. Only the threshold differs, and the difference is large — Open WebUI uses 5px, Khoj uses 50px. Five pixels is inside the noise floor of a trackpad flick.

The most instructive artifact is Open WebUI's actual scrollToBottom, read from source. It scrolls three times across two animation frames, and the comment explains why:

// content-visibility: auto causes the initial scrollHeight to be based on
// estimated sizes (contain-intrinsic-size). After we scroll, previously
// off-screen messages become visible and the browser resolves their actual
// heights, which shifts scrollHeight. Re-layouts can cascade across frames
// (new sizes reveal more content, triggering further size resolution), so
// we re-scroll across two animation frames to land at the true bottom.

— src/lib/components/chat/Chat.svelte, read 2026-07-25. A virtualization optimization created a correctness bug in scrolling; the fix is three stacked scrollTo calls and a paragraph justifying them. This is what polish costs at the bottom.

Streams that outlive their connection

LibreChat rebuilt streaming around a job that records deltas server-side, so a dropped socket replays instead of losing the response:

"On reconnect, the server rebuilds the content streamed so far from the job's recorded deltas. The missing content is delivered in a single sync event. Streaming continues from the current position." librechat.ai/docs/features/resumable_streams

Stated purpose: survive "network drops, browser refreshes, and server restarts," keep tabs in sync, switch devices mid-stream. The cost is real — #11702 documents truncated responses when a subscriber connects late — but the failure it eliminates is the one Open WebUI still has (see Theme 8).

Reusable patterns

  • Deltas on the wire, deltas in the store. Never re-send or re-assign the cumulative buffer. Cost scales with what changed, not with what exists.
  • One coalescer, not two. Batching is correct exactly once per pipeline. Layered rAF adds latency and subtracts nothing.
  • Freeze everything but the tail. Only the streaming message re-renders; every prior message is memoized and inert.
  • Near-bottom gate, generously sized. Auto-scroll only when the user is already at the bottom. 50px, not 5px.
  • The stream has an id. If the response only exists inside one HTTP connection, every disconnect is data loss.

How Kitty differs today

Verified against source, 2026-07-25

Gap  Kitty has the exact defect open-webui#23733 describes, at the store and render layers. The stream loop appends to a cumulative string and rewrites the message list on every token:

accumulated += chunk.content
updateChat(chat.id, (c) => ({ ...c, messages: c.messages.map(
  (m) => (m.id === aiMsgId ? { ...m, content: accumulated } : m)) }))

state/KittyContext.tsx:541–542 Corrected — originally cited as 543–544

Every token maps the full message array and allocates a new object per message. Downstream, ChatMessage feeds that whole accumulated string to ReactMarkdown with remarkGfm and rehypeHighlight (ChatMessage.tsx:183–215) — a complete markdown parse plus syntax highlight, per token. And there is no React.memo, memo(), or useMemo anywhere in ChatMessage.tsx or KittyThread.tsx (grep, 2026-07-25), so prior messages re-render alongside the streaming one. A 2,000-token reply in a 40-message thread is 2,000 full-thread re-renders and 2,000 full markdown parses.

Ahead  Scroll is already solved, by delegation. KittyThread uses assistant-ui's <ThreadPrimitive.Viewport autoScroll> with a ScrollToBottom control gated on isAtBottom (KittyThread.tsx:59, 116–124). Kitty gets, from a dependency, the behaviour four projects in this corpus are still hand-rolling. Worth a runtime check — the threshold is the library's, and 5px-vs-50px is the difference between working and not — but architecturally this is the right call and the reason to keep it.

Gap  No stream identity. Chat streams over a fetch body reader (lib/chat-client.ts:51) with no server-side job and no resume. If the connection dies, the reply dies. Note the asymmetry: Kitty's signal SSE already has bounded exponential backoff, 1s doubling to 30s, with an onOpen resync hook and a comment explaining why it owns the retry instead of trusting EventSource (lib/sse.ts:41–72). The care exists in the codebase; it just isn't on the path that carries the actual conversation.

Proposals — non-authoritative

Suggestions only. Nothing here is scheduled, owned, or decided.

Stop re-parsing the past. Memoize ChatMessage on (id, content, isStreaming) and coalesce the streaming write to one per animation frame — one coalescer, at the store, per open-webui's reversal. Measure first: the structural defect is verified, but the research document's own Theme 2 records the counter-evidence — markdown parsing is fast at chat length, which is why this ships broken so often. If a profile of a long reply in a long thread shows nothing, not doing the work is the correct outcome.

Give the stream an id. Server-side generation job with recorded deltas, resumable by id. This is the prerequisite for the mobile backgrounding failure in Theme 8 and it is genuinely large. Named here for completeness, not advocated.

Theme 02Loading and empty states

The theme where absence of signal is read as failure. Also the thinnest section here — GitHub search returns almost nothing for "skeleton" or "empty state," because these defects get filed under other names.

What the best projects do

They eliminate dead air. Any gap longer than roughly a second between one visible thing finishing and the next starting gets a placeholder — and the placeholder is cancelled when its subject is cancelled. Empty states carry starter content that survives contact with typing rather than vanishing on the first keystroke.

Why they converged there

Because users interpret silence as a crash and act on that interpretation. Open WebUI's #22970 — "No loading indicator between tool call completion and LLM response, making it appear as if the response has stopped":

"users sometimes assumes the conversation stuck. Tried to solve it using a filter, but still not covering all the scenarios that causes this." @ctcanbol on open-webui#22970

The maintainer's full reply is "Intended behaviour, open to discussion." A gap in a streaming UI, closed as working-as-designed. It is the clearest example in the corpus of a deliberate decision that reads to users as a bug, and worth holding onto as a counter-example: the absence of a signal is itself a signal, and you don't get to opt out of sending it.

The mirror image is #21350, "Progress indicators are not cancelled then the output is stopped by the user" — a spinner that outlives its subject is worse than no spinner, because it is actively lying. And LibreChat#4476 puts the whole theme in its title: "Add loading indicator for file uploads to prevent system freeze perception." The system was never frozen.

Empty states that survive typing

Open WebUI's Suggestions.svelte (read from source) fuzzy-matches its starter prompts against the input as the user types, using Fuse.js at threshold: 0.5 over ['content', 'title']. The suggestions narrow instead of disappearing, so the empty state stays useful into the typing state rather than being a one-shot that punishes you for starting.

Reusable patterns

  • Every gap gets a name. Enumerate the transitions — tool call → model response, upload → index, retry → reconnect — and give each one a visible state. Silence is not a state.
  • Indicators are owned by their subject. Whatever cancels the work cancels the indicator, in the same code path.
  • Empty states narrow, they don't vanish. Starter content that filters against input is worth more than starter content that disappears at keystroke one.

Theme 03Error recovery and trust

The theme with the densest evidence, and the one where Kitty is furthest ahead — because fail loud is already written down as a non-negotiable.

What the best projects do

The mature ones make failure visible, attributable, and reversible. The immature ones swallow it. A title search for silently across the corpus returns a dense cluster, and almost all of it is still open:

IssueWhat is dropped, silently
open-webui#27411Errors in tool-call continuation rounds
open-webui#25144Unknown tool call returns empty result instead of an error
open-webui#25916AI note edits lost when the note is open in the editor
cline#10984"empty catch blocks silently swallow errors in 3 locations"
cline#12247reasoning-delta stream parts dropped — wrong field name
aider#5486Valid diff-style output discarded by edit-format auto-selection
aider#5376Pre-commit hooks bypassed by default via --no-verify

#27411 is the canonical anatomy. Three lines of code:

except Exception as e:
    log.debug(e)
    break

What the user sees: an empty assistant message with content='' and done=true. No error event to the frontend, no error field in the database, and the round-one text still on screen — so it reads as "the model answered with nothing." The reporter's fix needs no new machinery; it is to use the error path that already exists elsewhere in the same function.

The cost of an unhelpful error string

open-webui#8074 is the most-discussed issue in the corpus at 203 comments. v0.5.0 made WebSockets mandatory. Everyone behind a reverse proxy that didn't forward WS got two words: "Network Problem." The maintainer's reply contains the diagnosis the message should have carried:

"you need a proper websocket support going forward with 0.5.0+ I'll make a educated guess here and say you have a network misconfiguration (most likely your reverse proxy)" @tjbck on open-webui#8074

What users did instead:

"I had the same problem and after about an hour of trying to fix it i just reverted to v0.4.8."@Blygf, same thread

The actual fix, eventually posted by a user, is three lines of Apache ProxyPass ws://. The knowledge existed the whole time. 203 comments is what it costs to leave it out of the error message on a breaking infrastructure change.

Reusable patterns

  • An empty success is a lie. If a path can produce a zero-content result, it must be able to produce an error result. content='' and done=true is the worst possible pairing.
  • Errors carry the next action. "Network Problem" costs 203 comments; "WebSocket upgrade failed — your reverse proxy needs to forward ws://" costs zero.
  • Use the error path you already have. In #27411 and in most of the cluster, the correct handling existed metres away in the same file. Silent failure is rarely a missing capability; it is an unreached branch.
  • Reversibility can substitute for confirmation — see Theme 4 — but only if the undo is trustworthy and visible.

Verified against source, 2026-07-25

Ahead  Kitty already refuses the #27411 pattern, deliberately. A truncated stream throws rather than resolving empty:

Ahead  Interruption is narrated, not inferred. An aborted turn writes "⚠ generation stopped before completion" into the message, marks turnStatus: 'interrupted', and persists it (KittyContext.tsx:553–558). Open WebUI is still requesting this in #20987. Gateway errors likewise surface into the message body with the real error text (KittyContext.tsx:562–564) rather than a generic string.

Gap  One swallow, in the hottest path. Malformed SSE payloads are dropped without a trace:

} catch {
  /* skip malformed */
}

lib/chat-client.ts:101–103

This is cline#10984 and open-webui#27411 in miniature, and it violates Kitty's own non-negotiable #1. A provider that changes its delta shape — exactly cline#12247, where a renamed reasoning-delta field silently vanished — produces a short or empty reply here with nothing in the console to explain it. The fix is a console.warn and a counter, not an architecture.

Proposals — non-authoritative

Suggestions only. Nothing here is scheduled, owned, or decided.

Close the one swallow, then assert on it. Log malformed deltas with a per-stream counter, surface a non-zero count in the turn, and have any end-to-end run fail if it drops chunks. This converts a class of invisible provider-shape breakage into a test failure. Best-supported item in the document: three lines, and it closes a standing violation of non-negotiable #1.

Theme 04Agent visibility and task progress

The theme with a genuine, unresolved architectural disagreement between mature products — worth understanding before picking a side.

What the best projects do

Two coherent, opposed answers to "how does a user stay in control of an agent."

Confirmation modelReversibility model
WhoZed, Clineaider
MechanismGate actions before they happen; per-tool-call permission tiers; hunk-level accept/rejectLet it act, commit everything, make undo one keystroke
CostApproval fatigue; users flip on auto-approve and lose the benefitRequires total git discipline; nothing to review before the fact

Zed shows the work continuously and reviews it structurally:

"Responses stream in with indicators showing which tools the model is using."

"Follow the agent as it reads and edits files by clicking the crosshair icon at the bottom left of the panel. Your editor will jump to each file the agent touches."

"accept or reject each individual change hunk, or the whole set of changes made by the agent" zed.dev/docs/ai/agent-panel

Cline gates per call, and its own docs recommend a conservative default:

"Auto Approve is evaluated per tool call. When Cline is about to read a file, edit a file, run a command, or use the browser, it checks your Auto Approve settings for that category."

"Enable Read project files" ... "Leave edits, commands, browser, and MCP off until you have a specific reason." docs.cline.bot/features/auto-approve

The stated rationale is explicitly about attention economics: "It keeps you out of approval popups during routine work while letting you keep tight control over high-risk actions." Approval is a budget, and spending it on git status means having none left for rm -rf.

aider's maintainer refused the confirmation model for two years and counting. #649, opened 2024-06-06, still open:

"Right now the recommended approach is just to use /undo to revert a change if you don't like it. Or you can turn off auto commits with --no-auto-commits." @paul-gauthier, who then closed the issue

A user reopened the argument — "AI tools are still not entirely accurate and always require human review whenever possible before making a change" — and got "See my comment above. Is there a reason one of those solutions doesn't work for you?" This is a position, not neglect: every aider change is a git commit, so reversibility is cheap and total, and the bet is that cheap undo dominates expensive confirmation.

What the community said about that bet

aider#3362, "Inspiration From Claude Code," 47 comments, opened by the author of aidermacs:

"it's basically 'driving' the terminal to get the job done, instead of one prompt → one response it takes your prompt, breaks it down into steps and uses the terminal tools available... locates and looks at log files automatically with tail — looks at git logs for reference — notices when a file has changed externally since the last time it read it" @mneuhaus on aider#3362

And the dissent in the same thread, which is the more useful half:

"it's easy to burn through dollars with it... With Aider at least you can explicitly tell it what files you want to modify, while Claude Code might deci[de]" @Ixe1, same thread

Explicit scoping is simultaneously a cost control and an agency feature. Neither model has won.

Reusable patterns

  • Pick one model and commit. Confirmation and reversibility both work. Half-confirmation — a dialog you can't act on, or an undo that doesn't fully undo — works worse than either.
  • Permission tiers by risk, not by tool. Read is free, write is gated, execute is gated harder. Uniform prompting trains users to click through.
  • Show the call and the result. A tool call with no visible outcome is Theme 2's dead air wearing a badge.
  • Per-item state, not per-turn state. Three tool calls in one message need three independent statuses.

Proposals — non-authoritative

Suggestions only. Nothing here is scheduled, owned, or decided.

Resolve the mismatch between the tool-call UI and the unwired tool loop. Two coherent directions exist — wire the loop, or retire the UI that depends on it. Theme 05Onboarding and discoverability

What the best projects do

Honestly? In this corpus, badly — which is itself the finding. Onboarding is the least-mature theme across every project studied, and the requests are still open years later.

Open WebUI's OnBoarding.svelte, read from source, is 106 lines and is a splash screen: a 5-second SlideShow, a marquee, a gradient, a logo with a dark-mode onerror fallback, one getStartedHandler. No steps, no model check, no first-question guidance. It also doesn't render its buttons on some mobile browsers.

Continue has three separate open onboarding issues, including #12258 — "CLI: onboarding prompts even when ~/.continue/config.yaml already exists," an onboarding flow that can't detect it already ran. And cline#3352 — "Figure out a way to recommend cheap models, maybe part of onboarding?" — locates the real first-run problem: model choice is a cost decision, and new users have no basis for making it.

Discoverability fails the same way everywhere

open-webui#1008, open since March 2024, 36 comments, is a critique of which actions earn shortcuts:

"There's a shortcut for settings, which are rarely accessed and not keyboard-friendly anyway. On the other hand, I often edit the last prompt instead of asking followup questions and there's no shortcut to start editing it."

"Current WebUI shortcuts use three-key combinations, which are usually only used in text editors with several dozen shortcuts."@robertvazan

In the same thread: "I can't find the keyboard shortcuts." Answer: "Look at the bottom right corner of the screen." The feature shipped; the affordance didn't.

LibreChat#3664 argues for Cmd+K purely from conformity — "used by popular AI chat interfaces like ChatGPT and Claude, making it intuitive for users familiar with these platforms" — and while it sat, a user shipped an entire desktop wrapper to get "new chat" and "archive chat" on the keyboard. People will build an application shell around your app to obtain two shortcuts.

Reusable patterns

  • First run must answer "which model, at what cost." It is the only irreversible-feeling choice a new user faces.
  • Shortcuts belong on the frequent action, not the impressive one. Editing the last message beats opening settings, every time.
  • Two keys, not three. Three-chord bindings are for editors with fifty of them.
  • Onboarding must detect that it already ran — from real state, not just a flag it set itself.

Theme 06Settings and model switching

What the best projects do

They make settings verifiable. The recurring failure is not too many options — it is options that don't tell you whether they took effect.

IssueThe failure
open-webui#27061 Web loader ignores admin UI settings — reads frozen env values. The UI shows one thing, the process uses another.
khoj#1361 No connection test or health check for a local LLM in settings. You can enter a config but not learn whether it works.
cline#5620 Checkpoints silently re-enable after restart — a setting that resets itself.
cline#3965 "[UI bug, dangerous impact] Settings pane continues unselected task in background"
open-webui#27205 Model selector: tapping the info tooltip closes the whole picker on touch

Note what unites the first three: the settings UI is a second source of truth that drifts from the first. The eventual fix is always the same — read the value the system actually uses, and give the user a way to prove it.

Reusable patterns

  • Display the effective value, not the stored one. If env can override the UI, the UI must say so at the point of the control.
  • Every external connection setting gets a test button. Config without verification is a guess with a save button.
  • Hover affordances must have touch equivalents — an info tooltip that eats a tap is worse than no tooltip.

How Kitty differs today

Verified against source, 2026-07-25

Ahead  Settings surface real usage — calls and token totals from a live query (components/SettingsPanel.tsx:30, 140–150), rather than only accepting input. That is the "prove it" half most of the corpus lacks.

Partial  Model override is per-turn and clears itself after use (KittyContext.tsx:574–576, oneShot / setOverrideModel(null)) — a genuinely nice touch, and cleaner than the sticky-model confusion in the corpus. Undocumented, though; nothing tells the user the override was one-shot.

Gap  No connection test for a local model endpoint — khoj#1361 exactly. On a local-first product where the endpoint is the most likely thing to be misconfigured, that gap is larger for Kitty than it is for Khoj.

Proposals — non-authoritative

Suggestions only. Nothing here is scheduled, owned, or decided.

A test button next to every endpoint. One round-trip, latency and model name back, green or red. It reuses the doctor path that already exists (./kitty doctor --json) and turns the single most common local-first failure into a five-second check.

Theme 07Memory and context presentation

The theme where the corpus has converged hardest on a specific implementation discipline, and where Kitty has a gauge that is wired up but shows nothing.

What the best projects do

They show context consumption continuously, and — critically — they source that display from the same accounting the system acts on. LibreChat's #13670, merged 2026-06-13, is the best-specified example in the corpus:

"a gauge beside the chat input shows tokens used vs. max context for the currently viewed message branch, with a hover breakdown of context composition (messages, system prompt, tool schemas, summary, free space)"

"The design mirrors the backend's existing token accounting instead of re-deriving it client-side, with three layered data sources that degrade gracefully" LibreChat#13670

Two disciplines in one paragraph: no second source of truth, and layered degradation rather than a single source that breaks.

Why they converged there

Because context displays that lie are worse than no display, and the corpus is full of them: cline#10148 "Impossible token count"; #10375 "percentage display incorrectly caps at 32.8k"; LibreChat#13886 counter includes reasoning tokens; #13795 cache tokens double-counted.

And because when the number is wrong, the behaviour is wrong. cline#10637:

"i can see context usage bar actually run backwards to lesser value like 60k. after that, i often see Cline trying to redo the tasks already done before, or forgetting important informations... there's no way to tell when it is happening unless you are watching the context usage bar. there's no indication of context compacting"cline#10637

A commenter identifies the mechanism: the client hardcodes a 128k window even when the model advertises 1M, so compaction fires at 128k regardless of the user's setting. Silent compaction is amnesia the user experiences as the product getting dumber. cline#4389 adds the endgame — "Tasks become unrecoverable when hitting token limits — users can only 'Retry' or 'Start New Task'" — alongside a user's measured session growth of 100K → 200K → 400K → 800K → 11M tokens.

Everyone reinvents Projects

LibreChat#4848, 58 comments. Every top comment names the same external product, and the differentiator they name is not the folder — it is shared context attached to the folder:

"I use Claude Projects at work, it's a game changer for shared context across multiple chats. The biggest downside to the Claude implementation is the limited size of document context"@stitcombe on LibreChat#4848

The complaint about the incumbent is capacity, not concept. That is a gap a local-first product is unusually well positioned to fill.

Reusable patterns

  • One accounting. The gauge reads the same numbers the truncator acts on. Two counters always diverge, and the user believes the wrong one.
  • Layered sources, graceful degradation. Provider usage → per-call events → stored per-message counts. Never one source that silently fails.
  • Compaction is an event, not a background process. If context was dropped, say so, in the thread, at the moment.
  • Estimates must be labelled as estimates. A precise-looking wrong number costs more trust than an obviously approximate one.

How Kitty differs today

Verified against source, 2026-07-25

Gap  The context gauge is fully wired and renders nothing. The chain, verified end to end:

WhereWhat
KittyContext.tsx:428 Corrected setTokenCount(Math.round(chars / 4)) — a character-count estimate over the whole thread
app/page.tsx:149–150 tokenCount={k.tokenCount} maxTokens={200000} — passed down, with a hardcoded ceiling
InputBar.tsx:16–17 tokenCount?: number and maxTokens?: number declared in the props interface — and never destructured or rendered

So Kitty computes a context estimate, threads it through two components, and drops it. The scaffolding for the exact feature LibreChat shipped in #13670 already exists; the last ten lines are missing.

Gap  And when it is rendered, it will be a second source of truth by construction — chars / 4 computed in the browser, against a 200000 constant unrelated to the active model, while the gateway does the real accounting. That is precisely what #13670's "mirrors the backend's existing token accounting instead of re-deriving it client-side" was written to avoid, and precisely how cline#10375 and #10148 got their impossible numbers.

Watch  F0 is where cline#10637 gets decided. Kitty has no compaction yet, so it has no silent compaction — a real advantage, and a temporary one. The moment F0 lands, the question is whether a compaction event is visible in the thread. Cline's answer was no, and it cost them a still-open issue about the product appearing to forget.

Proposals — non-authoritative

Suggestions only. Nothing here is scheduled, owned, or decided.

Ship the gauge from gateway numbers, before compaction exists. Return real token accounting and the active model's real limit on the stream trailer, render it in InputBar where the props already arrive, and drop the chars / 4 estimate. Unverified dependency: whether the gateway can emit usage on a streamed response at all — most providers only return it when stream_options.include_usage is set, and that has not been checked through LiteLLM. If it cannot, the honest fallback is removing the dead props, not shipping a client-side guess.

If compaction is ever built, make it a visible event. Write a marker into the thread saying what was summarized. A design constraint on future work rather than work of its own, and it costs nothing if decided up front.

Theme 08Mobile

What the best projects do

Two failure classes dominate, and both are about the browser doing something the desktop layout never has to survive.

The keyboard. open-webui#20722 — "Mobile viewport doesn't resize when the keyboard appears" — has three duplicates (#16851, #20361, #14010). The response in that thread is a finding in its own right:

"I poked around the FE sources but couldn't make heads-or-tails of them. Trying to be helpful, I created a basic repo that illustrates how to resolve the issue." @alshdavid, open-webui#20722

He later returned having written an entire alternative frontend. A user rewrote the app rather than navigate its source. That is a statement about approachability as much as about the bug.

Backgrounding. open-webui#26844 and its duplicate #26315 — "Chat stuck on loading-dots after backgrounding the PWA mid-stream." iOS suspends the socket, the stream never resumes, the dots spin forever. This is the same failure LibreChat's resumable streams were built to eliminate (Theme 1) — mobile is simply where connection loss stops being an edge case and becomes the normal way a session ends. A commenter reports it on desktop Edge too, "around once per day of usage."

Everything else is smaller and predictable: touch targets (#27241), hover affordances that eat taps (#27205), wide markdown tables scrolling the whole conversation (LibreChat#13535), and autofocus that summons the keyboard uninvited (#25842).

Reusable patterns

  • visualViewport, not resize. The keyboard doesn't fire a resize on iOS. This is the fix behind four filed issues.
  • Backgrounding is a disconnect. Mobile makes stream resume mandatory rather than nice-to-have.
  • Wide content scrolls inside its own box. A table must never move the page.
  • Don't autofocus after a response. It summons the keyboard and eats the screen the user was reading.

How Kitty differs today

Verified against source, 2026-07-25

Ahead  The fundamentals are right and were clearly done deliberately: 100dvh rather than vh (app/page.tsx:25) and env(safe-area-inset-*) on all three chrome components — input, bottom nav, top bar (InputBar.tsx:154, BottomNav.tsx:33, TopBar.tsx:56). There is also an explicit compact mode threaded through the view tree rather than CSS-only responsiveness.

Gap  No visualViewport listener anywhere in src/ (grep, 2026-07-25). 100dvh handles the browser chrome; it does not handle the keyboard on iOS. This is open-webui's four-times-filed bug, and Kitty is currently unguarded against it.

Gap  Backgrounding mid-stream loses the reply, for the reason given in Theme 1 — the response lives inside a fetch reader with no server-side job. Kitty ships a PWA manifest (app/manifest.ts) and has PWA tests, so this is a path users will take.

Proposals — non-authoritative

Suggestions only. Nothing here is scheduled, owned, or decided.

Add the visualViewport listener. A dozen lines against the shell layout, and it pre-empts the single most-duplicated mobile bug in the corpus. Verify on a real device — per Kitty's own definition of done, code inspection doesn't close this one.

Cross-cuttingThe meta-pattern: polish dies in refactors

The most transferable finding in this research isn't in any single theme. It is that these products lose polish the same way, repeatedly, and it is never through a feature.

cline#8675 — missing focus indicators on approval buttons — was investigated down to root cause, and the chain is worth reading in full:

"the focus indicators were accidentally removed during a code refactor."

"1. July 2025: @kevinneung added focus border functionality... 2. Shortly after: PR #4569 ('Splitting chat view into multiple modular files') refactored the ChatView into separate files, and the focus state management was accidentally dropped during this refactor. 3. Additionally: In webview-ui/src/main.css lines 5-7, there's CSS that explicitly removes focus outlines from VSCodeButton components... This was added during the Tailwind v4 upgrade in PR #6872." investigation comment on cline#8675

Two independent, entirely reasonable changes — a file split and a dependency upgrade — each deleted part of the same accessibility affordance. Neither was a feature change. Neither had a test that failed. And it had happened before: cline#4650 notes "a fix was implemented but later removed."

This independently corroborates ~/kb/corrections/2026-07-24-run-it-dont-read-it.md — a cleanup commit silently killing a live subsystem — from a completely unrelated codebase. The pattern generalizes: polish lives in code that has no test, no ticket, and no obvious owner, which makes it exactly what a refactor drops.

The transferable rule

Every polish behaviour worth keeping needs one runnable check that fails when it breaks — focus outlines, near-bottom scroll gating, the stop-message path, the malformed-delta counter. Not a suite. One assertion each. Otherwise the next reasonable refactor deletes it and nobody finds out until a user files the issue for the second time.
