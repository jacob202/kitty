## F1 — `pr-auto-label` fails on every single PR (from #301)

`.github/labeler.yml` is written in the labeler **v4** schema; the workflow
pins `actions/labeler@v5`, which needs `changed-files:` /
`any-glob-to-any-file:` nesting.

Evidence — job 91080385359 on PR #315:

```
##[error]Error: found unexpected type for label 'area/backend'
         (should be array of config options)
```

The whole path-based labeling feature has never worked. PR #307 fixes exactly
this, but it was opened against base `copilot/review-session-history` instead
of `main`, so it cannot land as-is. Dependabot #315 wants to bump the action
5 → 7, which changes nothing until the config is migrated.

Fix: rewrite `labeler.yml` to v5 schema, and retarget #307 to `main` (or close
it and fold the change in).

## F2 — `pr-test-hints` has the wrong permission scope (from #301)

`.github/workflows/pr-test-hints.yml` declares:

```yaml
permissions:
  issues: write
  pull-requests: read
```

Creating a comment on a **pull request** is governed by `pull-requests`, not
`issues`, even though the REST path is `/issues/{n}/comments`. So every run
403s after doing all the work.

Evidence — job 91080385439:

```
message: 'Resource not accessible by integration',
url: 'https://api.github.com/repos/jacob202/kitty/issues/315/comments',
status: '403'
```

Fix: `pull-requests: write`.

## F3 — the risk guardrail hard-fails all 13 dependabot PRs (from #301)

`pr-risk-guardrails.yml` treats `requirements*.txt`, `pyproject.toml` and
`.github/workflows/**` as risky scope, then calls `core.setFailed()` unless the
PR **body** contains `Manual approval: YES`. Dependabot bodies never will.

Result: PRs 311–322 are permanently red on a gate no bot can satisfy, and any
PR that fixes these workflows fails its own guardrail. Confirmed failing on
#315 (job 91080385660).

This is arguably working as designed per non-negotiable #6 — dependency work
should not auto-merge. But blocking and *failing* are different things.
Decision for Jacob:

- **(a)** keep labeling, drop `setFailed` for `github.actor == 'dependabot[bot]'`
  — bots get the `risk/high` label, humans still get the hard stop; or
- **(b)** leave it, accept 13 permanently-red PRs as the cost of the gate.

Recommend (a). The label already carries the signal; the red X just trains you
to ignore red.

## F5 — `pull_request_target` across four new workflows (from #301)

All four use `pull_request_target`, which runs with a write-scoped token. The
current code is safe: `pr-auto-label` is the only one that checks out, and
under `pull_request_target` `actions/checkout@v4` defaults to the **base** ref,
so no untrusted code executes. Nothing to fix today.

The hazard is future edits. Adding `npm ci`, `pip install -r`, or a
`ref: ${{ github.event.pull_request.head.sha }}` to that checkout turns it into
arbitrary code execution with a write token. Worth a NOTE comment at the top of
`pr-auto-label.yml` so a future agent doesn't wander into it.

## F7 — chronicle peak-hour tip is in UTC (from #302)

`gateway/chronicle_service.py:hourly_distribution()` buckets by
`datetime.fromtimestamp(..., tz=timezone.utc).hour`, and `_tip_peak_hour()`
turns that into user-facing advice:

> You tend to be most active around 05:00 (morning). Scheduling a standing
> brief with Kitty at that time can help prime your day.

Jacob is UTC-4 in summer. A 01:00 local session reports as 05:00 "morning", and
the tip then recommends scheduling a brief at the wrong hour. It is not just
cosmetic — the tip tells him to act on it.

Fix: bucket in local time (`.astimezone()`), or thread the configured timezone
through. Low effort, user-visible.

Also minor, same file: `model_usage()` returns `most_common(5)`, so
`summary.model_spread` silently caps at 5; and `_tip_model()` claims "you're
using a single model" when the real situation is every chat has no `model` key
and collapses to `"unknown"`.

## F11 — the health gate broke all 14 browser smoke tests (regression, in window)

**Correction to an earlier read of this file: `browser-smoke` does not predate
the window. It broke inside it.**

Evidence — same workflow, two commits:

| commit | when | browser-smoke |
|--------|------|---------------|
| `8790c21` (PR #301 merge) | 03:39 | **success** |
| `aae7577` (PR #325 merge) | 12:04 | **14 failed** |

The health gate landed between them, in `8828019 feat(ui): health gate, PWA
dismiss, builder breakdown, model display names`.

Mechanism: `browser-smoke` in `.github/workflows/tests.yml` starts **only** the
Next.js server —

```yaml
- name: Start server
  run: node node_modules/next/dist/bin/next start -p 4000 &
```

— with no Python gateway behind it. So `fetch('/proxy/health')` in
`KittyRuntimeProvider.tsx:HealthGate` can never succeed, `state` goes to
`'down'`, and the component returns the "Gateway offline" panel **instead of
`children`**. `<main>` is never mounted, so every spec that waits on it fails:

```
Error: element(s) not found
  - waiting for locator('main')
  at tests/smoke/settings.spec.ts:26:38
```

Failures span both projects — `boot.spec.ts` "page has visible content",
`chat.spec.ts`, `navigation.spec.ts`, `mobile-layout.spec.ts`, `settings.spec.ts`
— i.e. the whole suite, not a mobile-layout quirk.

PR #325's retry loop does not help; it retries a fetch that structurally cannot
succeed in that environment.

This is a **test-environment** bug, not a product bug — gating the UI on a live
gateway is the intended behaviour. Fix the smoke suite, not the gate: stub the
health endpoint in a Playwright fixture so the specs exercise the UI.

```ts
// gateway/kitty-chat/tests/smoke/*.spec.ts (or a shared fixture)
await page.route('**/proxy/health', route =>
  route.fulfill({ status: 200, contentType: 'application/json', body: '{"ok":true}' })
)
```

The route must be registered **before** `page.goto('/')`.

Worth noting separately: nobody would have caught this from the UI, because the
gate is correct-looking. It only shows up as red CI — which had already been red
for other reasons since 03:39, so the signal was buried. That is the actual cost
of leaving main red.
