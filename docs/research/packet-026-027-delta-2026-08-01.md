### The eight-fact evidence contract

All eight render in `initiative status --json`: `blocked`,
`infrastructure_failures`, `worker_failed`, `operator_completed`,
`review_approved`, `pr_opened`, `done`, `exhausted`.

Two contract details are weaker than the packet's wording, both minor:

- **`blocked` carries no durable reason.** The contract asks for "the durable
  reason and next operator action." `next_action` exists but is derived from
  task state alone (`operator_review` / `complete` / `run`), not from why the
  packet actually blocked. The reason is recoverable from the event trail, so
  nothing is lost — it is just not in the rollup.
- **`counts_toward_budget` is derived, not persisted.** Budget neutrality is
  correct and proven, but it is computed from the attempt outcome rather than
  stored as a field. A future outcome added without updating
  `_BUDGET_CONSUMING_OUTCOMES` would silently start consuming budget.

## The one real gap: operator closeout is unreachable through `run-packet`

Packet 026 requires that a worker failure followed by an operator completion
and an independent review render as three separate facts. That workflow
**works** — RP-07 proves it end to end. But reaching it requires driving
attempts by hand, and the packet's own "visible demo" tells operators to use
`run-packet`.

Two behaviours combine to close the door:

1. **A review cannot be attached to a closed attempt.** After a worker fails,
   its attempt closes `failed`. `record-review` on it returns
   `error: attempt 6 is closed (failed)`. So the operator's work needs an
   attempt of its own — which is the right model, not a bug.

2. **`run-packet` consumes the entire budget on failure.** Its repair loop
   retries until the budget is gone. A packet with `max_attempts: 3` and a
   failing worker ends at 3/3 in a single invocation. Raising the budget does
   not help — the worker eats whatever you give it.

The result: after any `run-packet` run that fails, `start-attempt` returns
`has used N/N attempts; operator intervention required` — and there is no CLI
verb that performs that intervention. `queue edit` exposes `--title`,
`--description`, `--priority`, `--acceptance`, `--allowed-paths`; there is no
`--max-attempts`. The error names an action the tool does not offer.

**Reproduction** (the harness does exactly this):

```bash
./kitty builder initiative run-packet <init> <packet> --worker-command '["false"]' --no-governor
./kitty builder initiative start-attempt <init> <packet>
# error: <init>/<packet> has used 1/1 attempts; operator intervention required
```

**Smallest honest fix:** add an operator verb that grants one further attempt
with a recorded reason — e.g. `./kitty builder initiative grant-attempt <init>
<packet> --reason "<why>"`, emitting an `attempt_granted` event so the rollup
still shows the worker failed, the operator intervened, and why. That keeps
the "never rewrite worker history" rule intact and makes the error message
true. It is one command plus an event type; no schema change and no new state.

Until then the workflow is reachable only by driving `start-attempt` /
`record-implementation` / `record-review` / `close-attempt` manually, which is
what RP-07 does and what any operator would have to do.
