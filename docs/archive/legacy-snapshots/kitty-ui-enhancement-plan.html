1. Builder Queue — Staleness, Requeue & Recovery

Current State

The Builder execution pipeline has sophisticated lease fencing, expired-lease recovery, and run reconciliation logic in the backend — but none of it is surfaced to the UI.

ComponentStatusDetails
builder_queue_leases.py ✓ exists recover_expired_leases() — scans claimed tasks, requeues expired leases. Updates claim_version, records events. Returns {claimed_requeued, running_blocked}.
builder_queue_runs.py ✓ exists reconcile_worker_runs() — requeues dead claimed tasks during reconciliation. Returns {claimed_tasks_requeued, ...}.
builder_cli.py ✓ exists CLI commands recover-leases and reconcile-runs exist — but are CLI-only, not callable from the web UI.
builder_control.py ✗ incomplete Only 5 actions: run_next, pause, resume, cancel, cleanup.
Missing: requeue, recover_stale, reset_budget, retry_failed.
BuilderSurface.tsx ✗ read-only BuilderControls shows pause/resume/cleanup. Dead packets are shown but user can only "clean up" (delete). No requeue button. No staleness indicator.
Packet staleness ✗ no detection Packets stuck in claimed/running for extended periods are not flagged.
Errors found:
  • BuilderSurface.tsx:347-354 — Zombie packets (cancelled/failed) get a "clean up dead work" button that deletes them with no option to requeue.
  • builder_control.py:28-33 — The action_map hardcodes 5 strings. Expanding it would let the backend call existing recovery functions from the UI.
  • No requeue or reset_packet in the Postgres action queue model — backend is wired for this via CLI but the UI-facing API surface is missing an adapter.

Execution Plan

Step 1: Add backend actions (builder_control.py)

Add 4 new actions that map to existing backend functions:

action_map = {
    "run_next":   "builder.run_next",
    "pause":      "builder.pause_initiative",
    "resume":     "builder.resume_initiative",
    "cancel":     "builder.cancel_task",
    "cleanup":    "builder.cleanup",
    // NEW:
    "requeue":        "builder.requeue_packet",    // reset packet state → queued
    "recover_stale":  "builder.recover_stale",     // call recover_expired_leases()
    "reconcile_runs": "builder.reconcile_runs",    // call reconcile_worker_runs()
    "reset_budget":   "builder.reset_budget",      // reset exhausted budget
}

Each new action needs a handler in the action queue:

  • builder.requeue_packet → reset packet task_state to 'queued', clear failure_kind, clear last_error, increment claim_version
  • builder.recover_stale → call builder_queue_leases.recover_expired_leases() (or initiative-scoped variant)
  • builder.reconcile_runs → call builder_queue_runs.reconcile_worker_runs()
  • builder.reset_budget → reset budget counters on a failed/blocked packet

Step 2: Add packet staleness detection

Define a staleness threshold (e.g. 10 minutes). Better: push into the backend BuilderStatusSnapshot so the runtime manifest includes staleness metadata without client-side math. Add packet.staleness field with {reason, minutes_stale}.

Step 3: Add requeue/recovery buttons to BuilderSurface

Per-packet: Requeue, Reset budget, Retry (requeue + reset).
Initiative-level: Recover stale, Requeue all failed.
Global: Reconcile runs (with confirmation dialog).

Step 4: Visual staleness indicators

Amber dot + "stale N min" for stale claims. Red dot + "stuck N min" for stale runs. Packet card gets a left-border color matching severity.

Files to modify

  • gateway/routes/builder_control.py
  • gateway/builder_queue_leases.py (if scoped recovery needed)
  • gateway/builder_action.py or equivalent action handler
  • gateway/kitty-chat/src/components/BuilderSurface.tsx
  • gateway/kitty-chat/src/lib/gateway.ts (add staleness fields to types)
Recommendation: The backend recovery logic is already built and working via CLI. The gap is purely UX/API surface — add 3-4 action strings to builder_control.py and wire them to existing functions. ~50 lines backend + ~80 lines frontend.

2. Experts — Chat Loading, Specialization & Prompt Editing

Current State

Two separate "expert-like" systems exist that barely connect:

ComponentDescriptionProblem
ExpertStrip (HomeState.tsx:809) Shows knowledge experts from /knowledge/experts. Lists label, book count, sample title, tags. Clicking navigates to 'chat' but does not create a new chat or inject expert context. The action is a functional no-op.
AgentPanel (AgentPanel.tsx) Standalone agent spawner: explorer, planner, coder, reviewer, researcher. Has goal input and spawn button. Not connected to knowledge experts. Agents run independently with no chat visibility. No way to edit prompt, personality, or skills.
/knowledge/experts Returns expert profiles with id, label, book_count, tags, formats, sample_title. No endpoint to start a chat with an expert. No endpoint to get/edit an expert's prompt.
SettingsShell.tsx:57-67 "skills & tools" admits agents are "available but unrouted" Self-documented gap.
Errors found:
  • ExpertStrip (HomeState.tsx:824) — onClick={() => onNavigate('chat')} navigates to chat but does nothing to create an expert-specific chat.
  • AgentPanel (AgentPanel.tsx:31-38) — spawned agent has no visibility in the chat view. No conversation interface.
  • No endpoint exists for POST /experts/{id}/chat — creating an expert-anchored chat requires backend support.
  • No prompt editing surface anywhere — the Chat interface has no systemPrompt or expertId field.

Execution Plan

Step 1: Extend the Chat model to support expert context

// types.ts — add to Chat interface:
expertId?: string | null          // which expert created this chat
systemPrompt?: string | null      // editable per-chat system prompt override

Step 2: Add expert chat creation (KittyContext)

Add handleNewExpertChat(expert: ExpertProfile): creates a new chat with expertId, generates a systemPrompt from expert profile (tags, specialties, book context), injects initial system message, sets chat title to expert label, navigates to chat view.

Template for expert system prompt:

function buildExpertSystemPrompt(expert: ExpertProfile): string {
  return `You are acting as ${expert.label}, a specialized AI with expertise in
${expert.tags.join(', ')}. Your knowledge is drawn from ${expert.book_count}
reference texts. Sample domain: ${expert.sample_title}. Respond with the depth
and precision expected of a specialist in this field. Always cite specific
frameworks or principles from your knowledge base when relevant.`
}

Step 3: Wire ExpertStrip buttons

// Before (broken): onClick={() => onNavigate('chat')}
// After:  onClick={() => onNavigate('chat', { expertId: expert.id })}

Step 4: Add expert prompt editing UI

Collapsible section above expert-anchored chats showing current system prompt. "Edit" button opens a textarea. "Reset to default" restores auto-generated prompt. Stored per-chat in chat.systemPrompt.

Step 5: Expert-specific skill chips

Map expert IDs/tags to suggested actions/commands shown as chip suggestions in the input area.

Step 6 (backend): Expert chat injection endpoint

POST /experts/{id}/chat/context returns curated system prompt + relevant knowledge snippets.
