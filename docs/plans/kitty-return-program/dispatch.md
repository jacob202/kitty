## How to run it for the best result per unit of usage

**Default:** start one existing ChatGPT conversation with the rollout-lead prompt below, using the connected desktop/file/shell tool and GitHub access that can actually operate the local repository. That lead dispatches R-1 and subsequent packets; Jacob does not need to paste each worker prompt himself. Confirm capabilities with read-only inspection. Included subscription use has limits; it is not API credit. Keep the current program available as files or in the conversation's project sources, and keep mutable state in Git/GAR/KB rather than repeatedly pasting the whole history.

Use a local Codex task when the worker needs reliable local edits, tests and worktree continuity. A smaller capable coding model is the first choice for bounded repair: Luna for narrow code/tests or reader review when available; Terra/Sol for a cross-file integration that exceeds it. Reserve Astra for resolving architectural contradictions, a difficult failed integration, or the final outcome judgment. These are routing defaults, not claims about fixed prices or guaranteed quotas. Check the selected tool's current capacity; do not keep retrying an exhausted lane.

**Do not put the entire program into one Work job.** A Work/cloud task is suitable only when that task has verified access to the necessary repository and inputs and can produce a reviewable patch/review without Jacob's local runtime. Good candidates are the bounded backend audit remainder or an independent review of a frozen diff. Local launchd, private local data, personal tool instructions and desktop/iPhone acceptance stay with a local operator. A Work result returns to the existing lead for integration; it is not a second authority.

Claude Code can implement or independently inspect using its existing included capacity once the same contract is loaded. CommandCode/DSH/OpenCode remain usable workers only when their actual provider, capacity, instructions and file access are known. Do not assume a paid API is included with a chat subscription. No additional plugin is required for the first dispatch if existing desktop and GitHub tools pass their capability check. Install nothing merely to standardize tool names.

Maximum useful fan-out initially: one product writer plus one independent non-overlapping workflow/audit worker or reviewer. Additional slots are not an instruction to fill them. Independent review must be independent of the implementer; a different model family is required where repo policy says so. When that policy requires governed paid review, prepare the candidate and request the actual bounded spend approval; subscription-based analysis does not silently replace a required merge gate.
