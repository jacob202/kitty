PrefaceBasis and method

The handbook says its Kitty claims were verified against source. I re-checked fourteen of them independently. Eleven held exactly. Three did not — and one of those three invalidates a whole theme.

Everything below is checked against the working tree at b78215e (the rewound gateway-packages, identical to main). The frontend was untouched by the abandoned refactor, so the handbook's line numbers still resolve, drifting by one or two.

What was consolidated first

The two research artifacts were in different places — MATURE_AI_PRODUCT_RESEARCH.md on the salvage branch, the handbook untracked on disk — and docs/PLANS.md differed by 125 lines between them. Both are now committed on research/mature-product-2026-07-25 so this reconciliation reads one coherent tree. docs/contract-migration.md was left untracked; it belongs to another session.

The headline

The handbook's central claim survives independent verification: Kitty's architecture is largely right and its signals are largely missing. The context gauge is computed and thrown away. The stop path is narrated but nothing else is. The SSE layer has careful bounded backoff and the chat stream has none.

But the reconciliation surfaces something neither document caught, and it is bigger than anything in either: Kitty's chat has no tool loop. Nothing ever sends tools to the model, so the tool-call UI can never render. Three of the handbook's eleven packets are built on that foundation.

And one finding in neither document

Kitty has three quarters of an agentic chat, wired to nothing. The chain, verified end to end this session:

  • The frontend request body (chat-client.ts:31–45) sends model, stream, messages and some ids. No tools.
  • The gateway payload (completions.py:263–272) spreads the body and adds messages/model/stream. No tools. grep for tool_call in completions.py returns nothing.
  • A tool schema builder exists — mcp_tool_bridge.py:129, get_tool_schema_for_llm() — and has exactly one consumer: an HTTP endpoint that hands it out (integrations.py:91–93). Nothing feeds it to a completion.
  • The frontend nonetheless parses delta.tool_calls (chat-client.ts:82–96) and renders ToolCallBlock.

The model is never told it has tools, so it never emits tool calls, so ToolCallBlock never renders. The handbook's Theme 4 describes its gaps as live user-facing defects. They are not reachable at all.

Question 6What needs runtime proof before it can be trusted

The handbook flags two of these itself. The rest are mine, and the third one is the important one — it can change a packet's size.

ClaimWhy source isn't enough
That the streaming defect is perceptible The O(N²) shape is verified structurally. But the research doc's own Theme 2 records the counter-evidence: markdown parsing is under 5ms for a 5KB message, which is why this ships broken so often — it works on everything you test with. Kitty is single-user with short threads. Profile a 2,000-token reply in a 40-message thread before ranking this first.

Deliverable CWhere I disagree with the research

Four substantive disagreements and one methodological one. The first is large enough to remove a whole theme.

C-1 · Theme 4 describes a feature that cannot run

The handbook rates ToolCallBlock as "Partial — shows intent, never outcome" and proposes packet #5 (tool-call results + per-call status, Small, D1). Both statements assume tool calls reach the user. They cannot.

chat-client.ts:31–45   request body: model, stream, messages, ids.   no tools
completions.py:263–272 payload:      body spread + messages/model/stream. no tools
completions.py         grep tool_call →  0 matches
mcp_tool_bridge.py:129 get_tool_schema_for_llm()
  └─ only consumer: integrations.py:93, an HTTP endpoint that returns it

The model is never told it has tools, so it never emits delta.tool_calls, so the accumulator never fills and ToolCallList returns null. The evidence for the gap is real; the conclusion that it is a user-facing defect is not. It is dead code. Packet #5 is struck and replaced by P2 (delete it, or decide to build the loop).

This also softens handbook #10 (decide the trust model). Confirmation-versus-reversibility only binds once an agent can act. Worth recording eventually; not due now.

C-2 · Onboarding already checks the server

The handbook says completion is "a self-set localStorage flag" and proposes deriving it from real state. But KittyContext.tsx:387 already fetches /proxy/onboarding and honours {onboarded, preferredName, theme} from the gateway. The derivation exists.

The real defect is narrower and sharper: line 385–386 returns early on the cached flag before the fetch, so a stale true wins over a server that says otherwise. That is an ordering bug worth two lines, not a packet worth rebuilding onboarding state. P3 above is the corrected version.

C-3 · The dead-air packet is moot

Handbook #6 proposes naming the gaps in runStream, specifically tool-call-complete → first-content-token. That transition cannot occur (C-1). The general send → first-token gap it would otherwise cover is already handled: ChatMessage.tsx:105 renders <TypingDots /> while streaming with no content yet. Struck.

C-4 · The #1 ranking rests on structure, not measurement

The handbook ranks memoization first on the strength of open-webui#23733. The defect in Kitty is real and I verified it. But the companion research document contains the counter-evidence in its own Theme 2: markdown parsing is genuinely fast for chat-length content — under 5ms for a 5KB message — which is exactly why this ships broken so often. Open WebUI hit the wall at 146k users' worth of long reasoning traces. Kitty is one user with short threads and no reasoning-trace rendering.

I have kept the packet and moved it to #5, with a profile as an acceptance criterion rather than a follow-up. If the profile shows nothing, the correct outcome is to not do the work — and that should be an allowed outcome, stated up front.

C-5 · "Nine of eleven are small" overstates the list

Three of the eleven are struck above. Of the remainder, one (the context gauge) has an unverified upstream dependency that could change its size, and one (mobile keyboard) cannot be closed without hardware. The honest version is seven packets, five of them genuinely small, one conditional, one hardware-gated. The document's underlying claim — that Kitty's gaps are signals rather than architecture — survives this correction intact, and it is the right claim.

What held up

Worth saying plainly, since the above is all objection: eleven of fourteen spot-checks confirmed exactly, including every claim in Themes 1, 2, 3, 7 and 8. The context-gauge finding — props declared at InputBar.tsx:16–17 and never destructured — is the single sharpest observation in either document, and I would not have found it.
