PrefaceBasis and method

The handbook says its Kitty claims were verified against source. Fourteen of them were re-checked independently. Eleven held exactly. Three did not — and one of those three invalidates a whole theme.

Everything below is checked against the working tree at b78215e. The frontend was untouched by the abandoned gateway-packages refactor, so the handbook's line numbers still resolve, drifting by one or two — except where noted, where they were simply wrong.

Status of this document, and what was removed from it

This is reference material. It is not authoritative. It does not set priorities, sequencing, effort, ownership, or what any other document should say. Roadmap authority remains the file named by docs/AUTHORITY_MAP.md.

The original version of this document overstepped that in five ways, all since removed:

  • A revised ranked roadmap (14 rows, with layers and sizes) presented as dropping into INITIATIVES_OPTIMIZED_2026-07-24.md. Research does not get to re-sequence the roadmap.
  • A list of continuity documents to edit before any engineering — .claude/STATE.md, .claude/HANDOFF.md, docs/PROJECT_STATUS.md, docs/ACTIVE_MISSION.md, CLAUDE.md. Those files have owners and their own process; a research pass is not it.
  • Ownership and scheduling decisions — which initiative belongs to which session, what "blocks everything," what to "not start here."
  • Deletion recommendations — striking initiatives, and a packet to delete ~120 lines of tool-call UI. The mismatch that motivated it is real and stated below; the remedy is not this document's call.
  • Measurements presented without evidence — a test-suite count, a module count, a rewrite-site count, an accessibility-issue count. None had a command attached. All are gone rather than repeated.

The headline

The handbook's central claim survives independent verification: Kitty's architecture is largely right and its signals are largely missing. The context gauge is computed and thrown away. The stop path is narrated but nothing else is. The SSE layer has careful bounded backoff and the chat stream has none.

And the re-check surfaced something neither document caught: Kitty's chat has no tool loop. Nothing ever sends tools to the model, so the tool-call UI can never render. Three of the handbook's proposals were built on that foundation.

And one finding in neither document

Kitty has three quarters of an agentic chat, wired to nothing. The chain, traced end to end:

  • The frontend request body (chat-client.ts:31–45) sends model, stream, messages and some ids. No tools.
  • The gateway payload (completions.py:263–272) spreads the body and adds messages/model/stream. Because it spreads the body, a tools key would pass through — nothing sends one. grep tool_call in completions.py returns zero matches.
  • A tool schema builder exists — mcp_tool_bridge.py:129, get_tool_schema_for_llm() — and has exactly one consumer: an HTTP endpoint that hands it out (integrations.py:91–93). Nothing feeds it to a completion.
  • The frontend nonetheless parses delta.tool_calls (chat-client.ts:82–96) and renders ToolCallBlock.

The model is never told it has tools, so it never emits tool calls, so ToolCallBlock never renders. The handbook's Theme 4 described its gaps as live user-facing defects. They are not reachable at all.

What this document does not do is tell anyone what to do about it. Building the loop and retiring the unreachable UI are both coherent; choosing between them needs product context this research does not have.

Section 3Where the research was wrong

Four substantive corrections and one methodological one. The first is large enough to remove a whole theme. All five have been applied to the handbook itself.

1 · Theme 4 describes a feature that cannot run

The handbook rated ToolCallBlock as "Partial — shows intent, never outcome" and proposed carrying tool results back with per-call status. Both statements assume tool calls reach the user. They cannot.

chat-client.ts:31–45   request body: model, stream, messages, ids.   no tools
completions.py:263–272 payload:      body spread + messages/model/stream. no tools
completions.py         grep tool_call →  0 matches
mcp_tool_bridge.py:129 get_tool_schema_for_llm()
  └─ only consumer: integrations.py:93, an HTTP endpoint that returns it

The model is never told it has tools, so it never emits delta.tool_calls, so the accumulator never fills and the block never renders. The evidence for the gap is real; the conclusion that it is a user-facing defect is not.

This also softens the proposal to decide the agent trust model. Confirmation-versus-reversibility only binds once an agent can act. Worth recording eventually; not due now.

2 · Onboarding already checks the server

The handbook said completion is "a self-set localStorage flag" and proposed deriving it from real state. But KittyContext.tsx:387 already fetches /proxy/onboarding and honours {onboarded, preferredName, theme} from the gateway. The derivation exists.

The real defect is narrower and sharper: KittyContext.tsx:385–386 returns early on the cached flag before the fetch, so a stale true wins over a server that says otherwise. That is an ordering bug worth two lines, not a rebuild of onboarding state.

3 · The dead-air finding is moot

The handbook proposed naming the gaps in runStream, specifically tool-call-complete → first-content-token. That transition cannot occur (correction 1). The general send → first-token gap it would otherwise cover is already handled: ChatMessage.tsx:106 renders <TypingDots /> while streaming with no content yet.

4 · The memoization ranking rests on structure, not measurement

The handbook ranked memoization first on the strength of open-webui#23733. The defect in Kitty is real and was verified. But the companion research document contains the counter-evidence in its own Theme 2: markdown parsing is genuinely fast for chat-length content — under 5ms for a 5KB message — which is exactly why this ships broken so often. Open WebUI hit the wall at a scale Kitty does not have.

The correct handling is a profile before the work, with "the profile shows nothing, so we don't do it" as an allowed outcome stated up front — not a ranking.

5 · Two line citations were wrong

The stream loop is at KittyContext.tsx:541–542, cited as 543–544. The token estimate is at line 428, cited as 427–428. Small in themselves, but they falsified the handbook's preface claim that every Kitty claim carried a checked file and line — which is why that claim has been replaced rather than trimmed.

What held up

Worth saying plainly, since the above is all objection: eleven of fourteen spot-checks confirmed exactly, including every claim in Themes 1, 3, 7 and 8. The context-gauge finding — props declared at InputBar.tsx:16–17 and never destructured — is the single sharpest observation in either document.

Section 4What needs runtime proof before it can be trusted

Everything in section 1 was verified by reading source. None of it was verified by running anything. These are the claims where that distinction changes the answer.

ClaimWhy source isn't enough
That the streaming defect is perceptible The O(N²) shape is verified structurally. But the research document's own Theme 2 records the counter-evidence: markdown parsing is fast at chat length, which is why this ships broken so often. Kitty is single-user with short threads. Profile a long reply in a long thread before treating this as a defect worth fixing.
That the gateway can emit usage on a streaming response gateway/routes/usage.py keeps a ledger with prompt_tokens / total_tokens, and completions.py:275–289 already has a trailer mechanism to hang it on. But most providers only return usage on a streamed request when stream_options: {include_usage: true} is set. Unverified through LiteLLM. This is the difference between the context-gauge proposal being small and being a provider investigation.
The assistant-ui near-bottom threshold Kitty inherits scroll behaviour from a dependency. 5px versus 50px is the difference between working and not, and the value is the library's. Flagged by the handbook, still unchecked.
The mobile keyboard fix Needs a real device. Kitty's own definition of done forbids closing this from code inspection.
Any TTFT number at all Targets cannot be measured until the model-routing path is confirmed running. Until then they can only be declared.
Accessibility findings from static analysis Never confirmed in a browser; some fraction will be false positives. The original version of this row gave a precise count with no command attached to it, and that number is withdrawn.

Section 5Open proposals

What the verified findings suggest someone could do. Deliberately unordered and unsized. Nothing here is a packet, a commitment, or a recommendation to delete anything. The original version of this section carried seven packets with sizes, acceptance criteria, dependencies and confidence ratings, and a ranked roadmap after them; that framing implied an authority this document does not have.

Best supported

Stop swallowing malformed stream deltas

Rests on
chat-client.ts:101–103 — catch { /* skip malformed */ }, verified.
Why
A provider that renames a delta field currently produces a short or empty reply with nothing in the console. It is also a standing violation of non-negotiable #1.
Caveat
None. This is the one item here with no open question attached.
Well supported

Fix the onboarding short-circuit ordering

Rests on
KittyContext.tsx:385–386 returning on the cached flag before the /proxy/onboarding fetch at 387, verified.
Why
A wiped database or failed import leaves a user marked onboarded with no way back.
Caveat
The cached flag should still win when the gateway is unreachable — the fix is ordering, not removing the cache.
Conditional

Render the context gauge from real numbers

Rests on
InputBar.tsx:16–17 — props declared, never rendered, verified.
Why
The user can see context filling instead of discovering it when the assistant starts forgetting.
Caveat
Blocked on an unverified question — whether LiteLLM surfaces usage on a streaming completion. If it does not, the honest fallback is removing the dead props, not shipping a client-side estimate dressed as a measurement.
Measure first

Memoize ChatMessage and coalesce the streaming write

Rests on
Full-thread map per token at KittyContext.tsx:541–542; zero memoization in the two render components. Verified structurally.
Why
Chat would otherwise degrade as threads grow; long reasoning traces are the stress case.
Caveat
Unmeasured at Kitty's scale. Profile first, and treat "the profile shows nothing" as a legitimate reason not to do it. Exactly one coalescer if it does happen — open-webui shipped a second one and reverted it in a day.
Hardware-gated

visualViewport listener for the mobile keyboard

Rests on
Zero matches for visualViewport in gateway/kitty-chat/src/, verified.
Why
Most-duplicated mobile bug in the eight-repo corpus.
Caveat
Cannot be closed from code inspection. Needs a phone.
Principle

One runnable check per polish behaviour

Rests on
The meta-pattern in the handbook — polish lives in code with no test, no ticket and no owner, which is what a reasonable refactor deletes.
Why
It is what keeps any of the above from silently regressing.
Caveat
Which behaviours are worth an assertion is a judgement call, not something this document can enumerate for someone else.
Decision, not work

Resolve the tool-call UI / no-tool-loop mismatch

Rests on
The end-to-end trace in section 1: no tools anywhere on the path, verified.
Why
Unreachable code currently reads as a shipped capability — including to research written on top of it.
Caveat
This document deliberately does not recommend a resolution. An earlier version proposed deleting roughly 120 lines across four files. Whether to build the loop or retire the UI is a product call with context this research does not have; the finding is the mismatch, not the remedy.

Considered and not proposed

A connection-test button per endpoint is a reasonable idea that overlaps ./kitty doctor --json, which already probes gateway and LiteLLM — likely a display problem rather than new capability. Compaction-as-a-visible-event is a design constraint on future work rather than work of its own.

Section 6Scope of this document

Stated plainly so nothing here is read as more settled, or more binding, than it is.

  • Not authoritative. This document, the handbook, and MATURE_AI_PRODUCT_RESEARCH.md are reference. They should not appear in docs/AUTHORITY_MAP.md. Their conclusions may graduate into the roadmap by a separate decision; the documents themselves stay as receipts.
  • Source, not runtime. Every Kitty claim here was verified by reading code. None was verified by running the app. Section 4 lists where that matters.
  • Line numbers are pointers. They were correct on 2026-07-25 and drift with any edit.
  • External-project claims are quotes, not reproductions. Counts, thresholds and performance figures attributed to other repositories are what those threads report.
  • No opinion offered on other documents. An earlier version audited the continuity and status documents and prescribed edits to them. Whatever is true about their freshness, correcting them is their owners' process and not a research output.
